# 新岛铁道启动器初步计划

更新日期：2026-10-25。需求依据：[新岛铁道启动器界面与更新方案.pdf](新岛铁道启动器界面与更新方案.pdf)（5 页，用户提供）。

本计划按该 PDF 重写，取代旧稿中“先保留 Prism 首页、自动更新暂列后续”的建议。自定义进入页、首次配置简化和一键下载／更新现纳入计划；两种更新方案尚未定案。文中区分已明确的需求、待验证行为和实施建议，不将设计稿中的疑问当作已经具备的功能。本次仅整理文档，尚未实现下列定制。

## 1. 产品目标与页面关系

在 Prism Launcher 基础上制作新岛铁道专用启动器。启动后默认进入自定义页面，玩家可在这里下载、更新和启动新岛铁道；通过「进入 Prism」按钮进入原有 Prism 主页，保留其通用实例管理能力。

优先复用 Prism 现有启动实例的流程。是否复用安装流程，取决于后续对两种更新方案的验证。核心目标是让玩家容易操作，并通过自托管资源或完整预置包减少安装时的额外下载，改善国内下载体验。

## 4. 下载、更新与启动的共同流程

进入启动器时默认检查新岛铁道整合包更新。自托管发布位置为用户服务器上的 copyparty，具体包 URL 和元数据格式待确定。

| 本地与远端状态 | 进入页主要按钮／行为 |
| --- | --- |
| 本地没有新岛铁道实例 | 「下载游戏」 |
| 本地版本低于最新版本 | 「更新游戏」 |
| 本地已经是最新版本 | 「启动游戏」；调用 Prism 启动对应实例的流程 |

版本比较应将 `1.6` 视作 `1.6.0`，支持后续 `1.6.X`，不能简单按字符串排序。最新版本可从包名读取，也可通过独立 JSON 获取，PDF 未选定其一。

需可靠识别新岛铁道实例，可考虑专用标记文件或其他可靠方法；实例标识、版本记录格式和多个实例之间的选择规则尚未确定。检查更新失败、本地版本高于远端、下载失败等状态的交互也需要补充设计，不将“无法检查”误认为“已是最新”。

未登录账号时，PDF 预期沿用 Prism 的账号选择／登录流程；当前是否会自动弹出、缺少账号时具体如何处理，需要源码和实际运行验证，尚未确认。

## 5. 一键更新的两个备选方案（PDF 第 4–5 页）

### 方案 1：全量包导入为新实例，保留旧实例

1. 在 copyparty 发布包含所需文件的全量整合包，目标包括 Minecraft 实例和 Forge 所需内容，减少或避免导入后的二次下载。
2. 启动器读取包名或独立 JSON 中的最新版本，与本地新岛实例版本比较。
3. 点击「下载游戏」或「更新游戏」后，下载包并走 Prism 安装新实例的流程。
4. **更新时不删除旧实例**，安装新的实例；安装成功后如何选定新实例为首页启动目标，需要明确。
5. 本地为最新版本时，按钮变为「启动游戏」，使用 Prism 原有启动代码路径。

对识别为自家新岛铁道整合包的安装，按用户要求默认跳过“非 Modrinth 来源模组”的安全警告。识别自家包的方法待讨论，PDF 没有要求必须使用密码学方案；此需求应限定在自家包，不扩大为对所有导入包关闭提示。

待验证：Prism 接受哪种完整实例包、导入是否仍会补下载、Minecraft／Forge／库／资源等实际需要覆盖哪些内容，以及登录与运行环境下载能否与资源预置分开处理。“全量包”目前是目标，不是已验证的离线安装能力。旧实例的用户配置、截图、存档等是否迁移到新实例，PDF 未规定，另行讨论。

### 方案 2：专用实例管理，自行下载与原位更新

1. 将新岛铁道实例作为一种特殊实例管理。
2. 自行实现文件下载和原位更新（in-place），绕过 Prism 的整合包安装流程。
3. 使用自托管资源，或将相关内容直接包含在包中，目标同样是安装后几乎不再下载，或完全不再下载。
4. 尽量复用 Prism 的启动能力；具体实例集成方式需验证。

待验证：Prism 是否支持自定义 Minecraft／Forge 下载源、能否完整预置运行资源、哪些下载步骤仍不可省略。方案 2 还需定义文件清单、版本状态、覆盖与删除范围，以及失败恢复；对用户文件的处理规则必须明确后再实现。

### 选型前要获得的证据

| 比较点 | 方案 1 | 方案 2 |
| --- | --- | --- |
| 更新方式 | 安装新实例，保留旧实例 | 在专用实例中原位更新 |
| 安装逻辑 | 优先复用 Prism | 自行实现下载与更新 |
| 全量预置能力 | 实测完整包导入后还会下载什么 | 核查自定义源与文件管理能否覆盖需要的资源 |
| 用户数据 | 明确新旧实例之间是否迁移、迁移什么 | 明确哪些文件可覆盖、删除，哪些必须保留 |
| 失败处理 | 避免将未完成的新实例设为启动目标 | 设计更新中断后的可恢复状态 |

先核查源码并做最小验证，再向用户展示结论和取舍，由用户确认方案。当前不把“方案 1”视为默认已选，也不因方案 2 更自主就直接重写安装系统。

## 6. 实施顺序与验收

以下是将 PDF 需求落地的建议顺序，尚未开始代码实施。

1. **恢复可靠的本地验证环境。** 处理辅助程序 Qt 运行库问题；在独立数据目录验证 GUI，不直接重跑会反复弹窗的测试。验收：主程序与辅助程序加载匹配的依赖，验证过程不持续干扰桌面。
2. **核查 Prism 的现有能力。** 列出首次向导设置、实例导入与启动路径、账号处理、自定义下载源及资源预置能力。验收：提供实际代码或实验依据，遗漏的首次设置已询问用户。
3. **确定更新方案与数据约定。** 对比两方案，确定版本来源、实例标识、自家包识别、用户数据处理和更新失败行为。验收：有明确选型和测试输入，未把未知能力写成承诺。
4. **实现自定义进入页与首次预设。** 按 PDF 布局、字体、色彩和三项预设实现，保留进入 Prism 主页的入口。验收：默认进入定制页，视觉与参考图一致，首次设置按确认结果初始化。
5. **连接下载／更新／启动。** 接入 copyparty 发布信息、版本比较、进度、速度、ETA 和实例启动。验收：无实例、旧版本、最新版本分别显示正确按钮；`1.6` 与 `1.6.0` 判断相等；按所选方案处理更新。
6. **实际整合包验证与交付。** 验证首次安装、更新、启动、账号缺失及网络失败；确认自家包警告豁免范围。方案 1 检查旧实例仍保留，方案 2 检查受保护文件及恢复行为。最后再确定便携包或安装器的交付方式。
